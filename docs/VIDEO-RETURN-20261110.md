# 画面回传与重连改进（dev，2026-11-10）

## 证据与边界

用户反馈点击后真机反应快、网页画面慢。排查首先遇到独立的网页通道阻塞：新建 WebSocket 的 TLS 握手超时，但同一 FRP 端口上的认证 RPC 正常。手机本地也能复现 TLS 超时；结束已核实身份且卡在 futex 的一个原生子进程后，TLS 与网页画面恢复，主服务及 FRP 未重启。详见 `FORWARDING-RECOVERY-20261110.md`。

恢复后浏览器实际使用 WebRTC、H.264、UDP 直连，媒体 RTT 约 28–50 ms，不是所有视频都经香港服务器中转。浏览器统计样本平均解码约 2.5 ms/帧、抖动缓冲约 40 ms/帧。但测试窗口即使报告 visible/focus，1.5 秒仅发生 2 次 requestAnimationFrame；在这种绘制受限状态下，10 次黑白切换点击到 canvas 更新的中位数约 1035 ms、最大 1202 ms。该结果受测试浏览器绘制限制，不能直接代表用户 Edge，也不能拿媒体 RTT 冒充点击延迟。

## 修改

- 首次及重新连接先协商 WebRTC，不再立即同时启动旧 WebSocket H.264 软件采屏/解码路径。WebRTC 不可用或失败后使用 JPEG 回退，540 像素宽（本机 scale=0.5）、5 FPS、quality=25，适合操作和看状态。
- 回退只保留最新待解码图片；解码结束即释放 bitmap。WebRTC 首帧真正可绘制后才关闭回退；触控通道与视频恢复仍分离。
- 对 detached video 的帧回调增加 100 ms 有界检查，回调停顿超过 150 ms 且确有新的解码帧才绘制最新画面。不会把已解码旧帧排队重放，也不会仅凭播放时钟增长把静止画面计为新帧。页面隐藏/暂停时原有清理逻辑仍停掉视频和定时器。
- 保留信令顺序、ICE 暂断宽限、首帧超时和重试退避，不修改页面布局、主分支、设备权限和账号数据。

原生阻塞进程与 H.264 回退并行重连有时间关联，但尚未拿到原生模块内部锁的堆栈；删除这条回退路径是降低复发风险的规避措施，不宣称已修复原生库的所有死锁。

## 验证

13 项视频专项测试、7 项转发适配测试、vue-tsc 类型检查和 Vite 构建通过。新增覆盖：帧回调停顿时只画最新解码帧；JPEG 丢弃中间帧和关闭后释放 bitmap；RTC 优先启动、失败回退及恢复清理。真实手机上线后的数据在验收后补入；不提前标记持续在线验收通过。
