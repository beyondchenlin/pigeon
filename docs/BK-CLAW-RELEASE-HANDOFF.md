## 正式包与安装迁移

- 用户已选择正式包**独立安装、保留现有测试版**。建议正式包名 `com.beyondchenlin.bkclaw`；旧测试包 `com.beyondchenlin.bk101.nativemcp` 继续保留。把最终包名、launcher 组件和 MCP 连接文件路径明确告知 Pigeon 项目，不得让两端分别猜测。
- 产品版本使用 `BK CLAW 0.1.0`，并在关于页、构建清单和发布说明中同时标明 Mika 基线；Android `versionCode` 在本正式包后续发布中单调递增。对旧测试包与正式包分开处理版本比较，不把 `0.1.0` 误判成测试版的自动升级。
- 正式包与旧包不同签名、不同包名，应允许并存。不得卸载旧应用、清除数据、覆盖用户模型配置或迁移密钥而无用户操作。若无法安全迁移配置，明确提示首次在正式版配置模型；不要求用户发送 API Key。
- 使用真正的长期正式签名，先查找已有签名材料；没有时建立安全的密钥管理与恢复方案。不要用 Android Debug 签名当正式签名，不把密钥、密码、令牌或个人配置写进 Git、提示词、构建日志或公开发行内容。验证签名一致性、包名、versionCode 和升级链。

## 更新渠道和发布

- 用户已选择**独立公开下载地址**，现有源码仓库保持私有；先确认或创建合适的公开发行渠道，不能把私有仓库访问令牌嵌进 APK。更新元数据和 APK 可公开读取，且必须使用 HTTPS、固定可信来源与下载完整性校验。
- 在关于页/更新检查中对接该渠道，完成真实“查到更新 → 下载 → 校验包名、版本、SHA-256 与正式签名 → 由系统安装器确认 → 原设置保留”的链路测试。必要时建立两个正式版测试构建验证升级；不要把调试包到正式包的覆盖安装说成已支持。
- 保留 Mika、Apache-2.0、NOTICE 和第三方组件来源及其对应发行材料；核对安装包中附带组件的源码提供与许可证提示。禁止将上游版权说成我们独立原创。
- 开发和验收通过、可回退且公开渠道确认后，按用户授权发布首版；发布记录包含 APK、校验值、来源提交、签名证书指纹、版本、渠道和已验证范围。真实未通过的项目列为未完成，不把调试包或模拟测试称作正式发布。

## 必须验证和交接

1. 运行与品牌、MCP 连接、用户主动关闭、更新比较及 APK 完整性有关的测试；构建后检查实际 APK 的包名、图标、版本、调试标志与签名，而不是只看源码。
2. 在授权试点手机上确认旧测试版保留、正式版独立安装、首次打开和模型设置、MCP 默认连接及用户主动关闭不被绕过。需要现场操作时给出最少步骤；不要删除用户数据。
3. Pigeon 需要兼容新旧包共存：新任务在明确策略下选正式版，在途旧任务仍绑定旧包和原任务编号；状态、取消、答复、接管及丢失回执均不得串任务或重新派发。手机端提供新正式包实际标识、版本、MCP 能力与测试结果，配合群控端实测。
4. 将“上游新版本发现 → 基线核对 → 品牌/连接改动重放 → 自动测试 → 候选包 → 真机及升级测试 → 正式签名发布”的可重复步骤和回退办法写入手机端项目；无用户明确要求不要建立后台自动更新或自动发布。
5. 交付时区分源码、APK、GitHub、公开发布页和真机各自状态，说明正式签名私钥的保管与恢复方式，但不展示密钥或密码。
