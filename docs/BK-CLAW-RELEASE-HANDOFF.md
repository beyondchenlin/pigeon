### applicationId 改造与核验

- `applicationId` 是 Android 安装包身份；它与 Kotlin 源码包名、Gradle `namespace` 是不同概念。优先只改安装身份，不为改名而全局替换 `com.wangzan101.mika` 或重命名源码目录；保留需要兼容的技术标识。
- 候选源码中 `app/build.gradle.kts` 设置了默认 `applicationId`，但文件末尾又应用 `bk/brand/android.gradle`，后者目前将其覆盖为 `com.beyondchenlin.bk101.nativemcp`。正式版应在品牌覆盖层或其他单一、可维护的权威配置中设置 `com.beyondchenlin.bkclaw`，并处理原覆盖，避免两处互相覆盖；不要仅修改默认值。已有 `devInstall` 和 `logs` 的包名后缀、`perf` 调试签名也要分别检查，正式发布只使用符合正式签名要求的构建变体。
- 检查合并后的 Manifest、`applicationId` 派生的 provider authority、明确写死的包名、Intent action、组件、文件路径、权限、MCP 连接和 Pigeon 的启动与发现逻辑；不要机械替换上游技术标识。正式版与旧版并存时检查端口、连接文件及其他共享资源是否冲突，按实际实现制定隔离和选路策略。
- 对每个要交付的 APK 用 Android 构建工具检查实际包名、launcher 完整组件名、版本、调试标志与签名，并在真机验证；将实际结果交给 Pigeon。更改 `applicationId` 会产生新应用身份，不会自动继承旧包的数据或成为旧包的覆盖升级。

## 更新渠道和发布

- 用户已选择**独立公开下载地址**，现有源码仓库保持私有；先确认或创建合适的公开发行渠道，不能把私有仓库访问令牌嵌进 APK。更新元数据和 APK 可公开读取，且必须使用 HTTPS、固定可信来源与下载完整性校验。
- 发布前核实公开渠道的平台、账号、访问控制、费用及维护责任，并检查 APK、元数据和发布材料不含私有源码、令牌、个人配置或内部日志。账号权限、费用或公开范围无法依据现有授权确定时，先准备方案并说明所需决定，不擅自扩大公开范围。
- 在关于页/更新检查中对接该渠道，完成真实“查到更新 → 下载 → 校验包名、版本、SHA-256 与正式签名 → 由系统安装器确认 → 原设置保留”的链路测试。必要时建立两个正式版测试构建验证升级；不要把调试包到正式包的覆盖安装说成已支持。
- 明确更新信任链：应用预置或通过可信途径获得正式签名证书指纹；对 APK 验证预期签名、包名与版本，SHA-256 用于完整性核对，不能把同一渠道同时提供的文件和哈希当作独立的来源认证。检查 HTTPS 重定向和下载来源限制、旧版本回退及证书轮换策略；任何校验失败均不得进入安装流程。用受控测试渠道和正式签名测试升级，避免测试版本号或元数据污染首发渠道。
- 保留 Mika、Apache-2.0、NOTICE 和第三方组件来源及其对应发行材料；核对安装包中附带组件的源码提供与许可证提示。禁止将上游版权说成我们独立原创。
- 开发和验收通过、可回退且公开渠道确认后，按用户授权发布首版；发布记录包含 APK、校验值、来源提交、签名证书指纹、版本、渠道和已验证范围。真实未通过的项目列为未完成，不把调试包或模拟测试称作正式发布。

## 必须验证和交接

1. 运行与品牌、MCP 连接、用户主动关闭、更新比较及 APK 完整性有关的测试；构建后检查实际 APK 的包名、图标、版本、调试标志与签名，而不是只看源码。
2. 在授权试点手机上确认旧测试版保留、正式版独立安装、首次打开和模型设置、MCP 默认连接及用户主动关闭不被绕过。需要现场操作时给出最少步骤；不要删除用户数据。
3. Pigeon 需要兼容新旧包共存：新任务在明确策略下选正式版，在途旧任务仍绑定旧包和原任务编号；状态、取消、答复、接管及丢失回执均不得串任务或重新派发。手机端提供新正式包实际标识、版本、MCP 能力与测试结果，配合群控端实测。
4. 将“上游新版本发现 → 基线核对 → 品牌/连接改动重放 → 自动测试 → 候选包 → 真机及升级测试 → 正式签名发布”的可重复步骤和回退办法写入手机端项目；无用户明确要求不要建立后台自动更新或自动发布。
5. 交付时区分源码、APK、GitHub、公开发布页和真机各自状态，说明正式签名私钥的保管与恢复方式，但不展示密钥或密码。

### 发布门槛、跨端责任与回退

- 以下均为发布必过项：正式 APK 的标识、版本、图标、非调试状态和签名检查；授权真机上的旧包保留及正式包并存、首次启动和模型设置；MCP 实际连接及用户主动关闭后不被绕过；正式签名版本通过受控渠道完成真实更新并保留正式版设置；Pigeon 新旧包选路与在途任务隔离的联合实测；发行材料、许可证、公开渠道和密钥恢复条件核验。每项记录设备或环境、构建与提交、操作、结果和必要证据；未运行、失败和受阻分别标明。
- 手机端负责提供实际包名、launcher 组件、MCP 连接契约、能力及测试包，并配合联合实测。Pigeon 仓库的选路、任务绑定、状态与回执隔离由群控端实现和验证；明确双方负责人和证据。如果群控端尚未完成上述必过联测，仅交付候选包和接口信息，不宣称跨端验证通过，也不公开发布首版。
- 回退方案应包括保留旧测试版、停止分发及必要时以更高 `versionCode` 发布修复包；不要承诺可直接用低版本覆盖安装，也不要在回退中卸载或清除用户数据。记录各方案的适用条件和限制。
