# PIGEON → BK 单机验收，2026-11-11

结论：已部署并验证真实模型任务完成、运行中取消、原生触控接管、request_id 去重和关闭连接后的人工占用回收。范围是一台 vivo V2220A、Android 14、移动数据链路；不是长期无人值守或多机规模验收。

## 环境与结果

- FIRERPA 10.9；BK 截套 0.1.37 (38)，沿用已安装 APK 与手机模型。未构建或替换 APK，没有服务器模型、聊天框模拟输入、Root 或网络切换。
- PIGEON 使用原 PostgreSQL、原设备鉴权与已有加密 RPC。API 和 worker 增量加载扩展，原媒体实现保留。
- 成功任务在 `mika-agent` 虚拟显示执行；原远控媒体显示主屏。验收时独立系统读取为电量 84%、Android 14、放电中。

## 现场发现与修复

1. 初次加载扩展后 FIRERPA 旧主进程等待一个已卡住的直接子进程，端口关闭但主进程未退出。核对 UID、可执行文件、父子关系和启动标识后，只终止该残留子进程，父进程自行退出。另修正维护启动器预先脱离会话造成的 `setsid EPERM` 隐患；后续受控加载两次正常退出并启动。没有证明手机 App 的所有历史“启动超时”都永久修复。
2. vivo 冻结了 BK 的后台线程，包括 `remote-accept`。首次提交回执未知，始终只查询原 ID `e92f0da9-aa2f-55c3-930e-bda342fd4458`；BK 回到前台后确认运行，再按已过期的时限取消，未重发创建动作。
3. FIRERPA 启动后，BK 无障碍开关仍开启，却收到了 unbound。经用户同意重连已有服务后发现，FIRERPA 再加载会重现；仅调用一次只读 `device_info()` 即恢复原进程的服务绑定。将此初始化加入新任务传输，随后真实设置任务成功。官方说明也声明 Android 8+ 可与其他无障碍服务共存，但本记录只证明当前固定版本组合。[FIRERPA 官方说明](https://github.com/firerpa/lamda/blob/10/README.md#ui-automation)
4. 原轮询挂在 `IOLoop.start`，实际运行时覆盖了该方法。改挂 `BaseAsyncIOLoop.start`，真实任务进度和取消由周期轮询持续写入数据库；观察脚本只读数据库即可看到变化。
5. 原生 socket 关闭后人工占用可能遗留。增加 socket/进程身份核验与失效占用清理，实测已消失的连接被清除；并发首条输入只申请一次占用，等待取消期间断开的旧输入不再交付。

## 验证与边界

- 既有 Linux 容器：29 项 AI 接口、传输、仲裁、事件循环和输入 guard 测试全部通过，0 跳过；启动会话语义的 2 项测试通过。
- Windows：69 项测试，56 通过、13 项环境跳过；POSIX 文件锁和运行时依赖检查已在 Linux 补验。
- 远控网页显示在线、控制已连接，视频为 360 × 796，解码帧数持续增加；保存了一张主屏证据。最终输入扩展的原生状态与触控握手另外验证。
- 模拟连接故障覆盖超时、404、未知回执、重启只查询、取消受理不等于终态。没有主动切断唯一远控通道做断网测试。
- timeout_s 是服务器监督时限；服务器或通道失联时不保证手机按时停止。未验收过夜稳定性、多设备、业务计划、账号配额或任意第三方工具的全局互斥。
