## 2. 实际落地的业务契约

| 参数 | 本轮支持及约束 |
|---|---|
| `version`（契约版本）、`kind`（任务类型） | 仅版本 1、浏览任务 |
| `duration_s`（业务时长） | 1～10000 秒；手机实际开始后使用单调时钟 |
| `clock`（计时方式） | 本轮仅自然经过时间；暂停和等待不会延长约定到期点 |
| `finish_timeout_s`（到期收尾时限） | 1～120 秒；超时继续报告未确认收尾，不能假定资源已释放 |
| `stop_timeout_s`（停止确认时限） | 1～120 秒，与到期收尾分别计量 |
| `progress_interval_s`（普通摘要周期） | 1～3600 秒 |
| `event_latency_s`（关键事件目标） | 1～30 秒；配置目标，不是已实测性能保证 |
| `budget.max_tokens`（模型累计用量阈值） | 1～10000000；预算和有效进展要求由用户明确填写 |
| `min_observations`（最少有效观测） | 至少 2 次 |
| `min_active_s`（最少有效时间） | 至少 1 秒，且不超过业务时长 |
| `max_stall_s`（最长无有效进展时间） | 1～10800 秒；迟醒不能用到期覆盖更早发生的停滞 |

监督范围按“120 秒启动余量＋业务时长＋到期收尾＋关键事件目标＋停止确认时限”推导。7200、60、30、30 秒的组合需要至少 7440 秒监督；显式更短的监督值被拒绝，整体上限保持 10800 秒。此推导不证明启动耗时或真实运行性能。

模型预算按已报告的输入和输出用量累计，在下一请求前及模型返回后的动作前检查。缺失用量、重试中未报告的用量会使任务失败关闭。单次已经发出的请求在返回时会跨过阈值，因此该值不是服务商账单的精确硬封顶。没有额外生成标题、结束判定或停止总结来绕过契约预算。

完整契约参与三端请求语义判断。同一编号修改时长、进展、预算或其他执行字段会明确冲突。

## 3. 持续执行、停止与结果

手机复用原有执行循环、工具、暂停入口及动作守卫。正常浏览进入本地“停留、观察、滚动、确认”循环，使用真实当前应用和任务显示；常规重复动作无需每次调用模型。目标改变、观测失败或动作未确认时，在同一任务中交回模型纠错。没有通过重复追加“继续”维持任务。

手机单独执行到期边界。到期后不开始新浏览动作；先采集本任务仍持有的显示，再按原资源清理路径收尾。进程级租约覆盖本地与远程任务，跨任务服务重建仍保留占用。严格显示释放失败时保留非终态，不发送真实结束确认，不允许新契约任务抢占。

结果保存实际开始和结束、当前阶段、最后有效进展、有效动作及观看进展、等待、暂停、停滞、异常、用量和结束原因。模型纠错期间的动画不计作有效观看。时长达到和业务成功是不同字段；进展不足、模型错误、预算耗尽和超期收尾均不能仅因到期而成功。

网页停止立即进入待确认；收到手机真实执行结束标志和合法终态后才释放占用。迟到运行快照不能覆盖终态。网页远控仍经过原桥接接管守卫；页面的“暂停画面”不是任务暂停。单机任务页没有新增单独的暂停或立即接管按钮，用户先停止确认，再进入原远控。

## 4. 普通摘要与关键事件

普通摘要按配置低频同步。关键状态修订使用既有认证连接上的有界等待，手机返回关键修订或 204 空响应；手机没有新增公网入口。服务器普通任务、事件等待、停止控制使用分开的执行资源。手机旧等待和新修订等待共同限制为四个等待名额，不能占满停止和查询连接。

模型错误和预算耗尽在慢截图、慢清理之前先发布非终态关键事件，保留真实原因。事件发生时间、服务器接收时间和新鲜度分别保存。断线后查询原收据，不重新创建业务；不能查清时保留待核对和占用。

## 5. 结束证据

截图仅来自本次仍持有的实际任务显示，在显示释放前采集；不从主屏兜底、不在查询时事后补采。记录设备、原任务、实际执行编号、显示编号、采集时间、帧时间、来源及是否迟补。

服务器核对任务真实结束、开始与结束时间范围，并要求截图清单、结果内证据和快照顶层的实际执行编号一致。图片经过大小、摘要、格式及分块完整性检查，持久化后才确认手机已归档。缺图记录可以明确归档，不能伪装为完整证据，也不会长期阻挡后续证据。

`tests/fixtures/bk-browse-contract-v1.json`（跨端合成样本）由手机真实生产序列化函数生成，含明确合成标记及合成图片。它验证协议与归档兼容，不是手机截图。生成入口是手机核心测试中的 `writeCrossEndFixtureFromProductionSerializers`（生产序列化样本生成测试）；输出位于核心构建目录的 `test-fixtures/browse-contract-v1.json`（样本文件），替换后需重跑跨端及接口测试。

## 6. 两轮代码审查

第一轮针对功能与架构，第二轮针对异常与可靠性；审查者独立读取实际源码，问题修复后再次复核。主要修复如下：

| 发现的问题 | 修复结果 |
|---|---|
| 只有到期账本，模型提前结束后没有持续本地浏览 | 接入真实本地循环，保留原执行器、工具和守卫 |
| 关闭动作后附屏时，成功滚动没有位置字段，循环不能接管 | 用既有本地观察读取真实目标，并在滚动后核实同一目标和进展 |
| 暂停与等待计入有效进展；模型纠错动画计入观看 | 分开计时基线，仅真实本地浏览阶段采纳观看变化 |
| 到期覆盖模型失败；查询继续增长最终时间 | 保留失败优先级，冻结终态结果和时间 |
| 服务销毁清掉界面登记，但旧运行仍在清理 | 新增进程级租约及旧运行查回，清理确认后释放 |
| 原显示释放吞掉异常 | 契约任务严格确认实际显示释放，失败保留租约和非终态 |
| 异常原因等到慢清理完成才通知 | 清理前发布带真实原因的关键修订 |
| 桥接只凭结束标签释放；等待挤占控制资源 | 三处释放统一核验真实终态；等待配额与控制资源分离 |
| 截图缺少执行时间及实际运行编号校验 | 服务端与网页均严格关联，错误证据不归档、不确认 |
| 主动查任务误用缓存；空事件时间显示为旧纪元 | 主动查询刷新，自动页面轮询缓存；空时间保持缺项 |
| 手机完整回归发现包依赖门禁、普通协议连接复用回归 | 去除执行层对具体能力包依赖；只关闭需要释放的长等待连接 |

在仓库根目录执行以下命令创建测试环境；不要把正式服务加入此网络：

```sh

docker build -f tests/Dockerfile.bk-mcp -t pigeon-bk-mcp-test:20261113 .
docker network create --internal pigeon-bk-contract-20261113
docker run -d --name pigeon-bk-contract-redis-20261113 --network pigeon-bk-contract-20261113 --network-alias redis-master --network-alias redis-lock01 --network-alias redis-lock02 --network-alias redis-lock03 redis:8-alpine redis-server --requirepass isolated
```
