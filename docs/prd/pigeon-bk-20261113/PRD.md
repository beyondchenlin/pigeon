# PIGEON 与 BK 解套协同执行总纲

## 一句话目的
让用户在 PIGEON 网页用自然语言安排单台或分组手机的任务，由服务器理解、调度和监督，默认交给手机上的 BK 解套自主执行，同时保留现有功能，减少手机接入和日常操作步骤。

## 技术栈
- 服务器：沿用 PIGEON 的 Python 后端及现有任务、设备和权限体系。
- 网页：沿用现有 Vue 前端，不迁移技术栈，不移动现有菜单位置。
- 手机：沿用 BK101 的 Kotlin／Android 实现和手机独立模型配置。
- 通信：复用已有 FIRERPA 手机连接，通过手机内部 MCP（模型上下文协议）接口调用 BK，不新增手机公网入口。
- 数据：复用现有存储，补充设备接入状态、任务关联与恢复记录，不另建平行任务系统。
- 模型：服务器与 BK 分别配置 API Key（接口密钥），可相同或不同，不要求互相复制。

## 功能清单
- 功能01：保留 PIGEON 现有 AI、模型、任务、脚本及点击滑动能力；默认执行方式为 BK，原生方式仍可选。BK 保持独立运行能力。
- 功能02：网页提供统一自然语言聊天入口，按设备名称、编号或分组安排任务，不要求先进入某台手机；目标有歧义或权限不足时不得误派任务。
- 功能03：手机接入现有 PIGEON 通道后，自动识别 BK 安装、版本和连接状态，自动完成受管设备的桥接与登记；缺少权限时明确提示，不让用户逐台填写路径、端口或令牌。原有手机配套软件优先不改，是否需要补改以能力核查为准。
- 功能04：BK 的受管连接模式默认开启，并在手机重启后恢复接入；保留用户主动关闭的选择，不能把主动关闭当成掉线偷偷重开。系统权限和后台启动限制无法满足时，显示具体原因。
- 功能05：复用现有任务体系支持立即、定时、循环和分组执行；跨手机并行，同一手机的屏幕操作互斥；任务不依赖用户持续打开网页。定时任务需明确时区。
- 功能06：服务器负责执行前的任务整理、目标选择和安排，BK 接收自然语言目标后使用手机自己的模型完成操作；已有脚本和流程继续保留复用，不要求服务器拆解每次点击。
- 功能07：网页统一展示每台手机的执行进度、等待用户、完成、失败和结果证据；支持停止任务及对任务追问作答，不能用接口已接收冒充实际完成。
- 功能08：支持两小时等长任务、进度保存、断线和重启后的状态核对与恢复；不再用统一十五分钟截断任务。发布、评论、私信等有外部影响的操作，恢复前先核对结果，避免重复执行；无法判断时明确等待处理。
- 功能09：按单机两小时、16 台分组、300 台及 3000 台容量目标分阶段建设和验收；不把架构设计或单机成功当作规模验证通过。大规模并发指标、部署配置和成本上限待确认。

## 验收标准
- 验收01 → 功能01：升级后原菜单位置及原有能力仍可使用，任务默认交给 BK，BK 脱离服务器仍可独立使用；删减原功能或强制共用模型配置视为未通过。
- 验收02 → 功能02：在统一聊天框指定设备或分组，系统生成准确的目标和任务；重名、越权或不存在的目标被明确拦截；派到错误手机视为未通过。
- 验收03 → 功能03：已连通 PIGEON 的新手机安装兼容 BK 并满足必要授权后，服务器自动发现并完成接入，网页显示真实状态；仍要求逐台手填连接参数，或把远控在线误报为 BK 可执行，视为未通过。
- 验收04 → 功能04：已启用受管连接的手机重启后可重新接收任务，旧任务状态仍可核对；用户主动关闭后保持关闭。恢复失败无提示、绕过关闭或丢失任务关联视为未通过。
- 验收05 → 功能05：关闭网页后，定时任务仍按指定时区触发；分组任务逐台有执行记录，不同手机可并行，同一手机不发生争抢操作；漏派、重复派发或错误提前结束视为未通过。
- 验收06 → 功能06：服务器与 BK 配置不同模型和密钥时，服务器完成任务整理，BK 使用本机模型执行；必须传入服务器密钥才能运行 BK，或服务器越过 BK 默认执行手机动作，视为未通过。
- 验收07 → 功能07：任务全过程能在网页查看与实际一致的状态、结果和证据，停止和追问答复可追踪；手机已完成却长期显示运行中，或仅收到请求就显示成功，视为未通过。
- 验收08 → 功能08：单机连续执行两小时并在结束后及时返回结果，不额外固定等待五分钟；模拟中断后先核对已有结果，再恢复未完成部分；重复发布、重复发送或盲目重跑视为未通过。
- 验收09 → 功能09：依次提供单机、16 台及后续容量阶段的实际记录；300／3000 台阶段须先确认负载、并发和资源指标，再按指标验收。未经实际验证不得标记为已支持。

## 技术栈说明

- 沿用 PIGEON Python 后端、Vue 网页与既有设备、用户权限、Job/DeviceJob（父任务／单设备任务）体系，不重新创建与它平行的群控任务系统。
- 沿用 BK101 Kotlin Android 程序。服务器模型负责理解和组织任务；BK 的模型负责执行手机操作。两端配置和计费分别归各自管理，不复制密钥。
- 正常链路：网页 → PIGEON 任务服务 → 已认证 FIRERPA 通道 → 手机本地桥接 → BK 本地 MCP → BK 自己的任务服务和 Agent（智能执行程序）。结果按原路径返回。
- MCP 是调用接口，不代替设备注册、批量队列、权限系统或任务数据库。现有内部服务可以直接调用既有适配，不要求每一跳重复套 MCP。
- 手机 MCP 保持回环访问，不为每部手机开放公网监听，也不要求 Windows 开发电脑持续在线或 USB 数据线持续插接。
- 固定源码基线：PIGEON（群控平台）仓库 `beyondchenlin/pigeon` 的 dev（开发分支），提交 `a57f3b5673364cdca78d5f6632e45beebf096ebd`；BK101（手机执行端）仓库 `beyondchenlin/bk101` 的 dev2（第二开发分支），提交 `3fe450246d8396a858bd653c0b79b669d01caf2c`。不得用默认主分支替代这两份基线。
- 本机项目位置为 `E:\qk\pigeon`（群控仓库目录）；已核实本地提交与群控固定基线一致，文档修订前已有9项已修改文件及3项未跟踪文件，须完整保护。两端固定源码、本机未提交候选和历史安装包分别记录，不能合并视为当前已部署产品；具体见下方现场核对表。
- 数据库产品、版本及具体迁移字段未重新逐项核实；本需求只约束复用现有存储和兼容迁移，不凭空指定替换数据库。

## 背景、目标与边界

用户需要的是面向用户的服务器网页产品，不是以后继续通过本次研发聊天逐台控制手机。用户应直接说“让美国组每天晚上八点浏览抖音两小时”，服务器负责解析、选组和安排，BK 自主执行。服务器监督任务，而不代替 BK 决定每次点击。本轮实施重点收敛为：一台已接入手机，立即执行一次约两小时的自主抖音浏览；服务器一次派发，低频同步进度，接收异常和完成结果，不持续看屏幕、不逐步遥控。正常闭环遇到具体问题再定位处理，随后再做分组、定时和16台阶段；原长期需求继续保留。这里的“一次派发”指一次业务执行，通信重试必须复用原提交身份而不能另建任务。

首轮面向用户的交付入口复用现有单机自然语言任务页面，至少能发起、查看进度、请求停止和查看结果；第一轮不要求先完成统一聊天选机。仅通过研发接口跑通时，结果标为技术链路验证，不能代替网页可操作验收。原菜单位置保持不变，后续统一入口仍按功能02落实。

## 详细功能

### 功能01 保留现有功能与独立使用
总纲对应：功能01。
使用者与前置条件：已有 PIGEON 用户和独立使用 BK 的用户。
输入与主流程：沿用既有模型配置、脚本、任务和设备入口；新建任务的执行方式默认 BK，需要时可显式选用原生能力；已保存的旧任务保持其原方式，不能迁移后悄悄改成 BK。
输出和可观察行为：菜单位置不变；既有功能可进入；任务明确显示执行方式；没有 PIGEON 连接时，BK 仍可在手机端本地使用。
边界、失败与恢复：BK 不可用时显示原因，不悄悄切到原生点击方式继续执行；切换方式须保留任务语义、权限与副作用边界。旧任务数据缺执行方式时按原行为兼容。
权限、保真或兼容限制：保留现有用户和设备权限，密钥各自管理；不得因迁移丢失旧脚本、历史收据或模型配置。

实现说明：现有 McpUsbSettings 根据 bootId（开机标识）作废访问状态，需将持久用户意愿与本次开机的短期连接信息分离；审查 BootRestoreReceiver、服务权限和监听发布。旧任务归属应由稳定受管身份和持久收据关联，不直接以复用旧令牌解决。详细身份迁移方案在实施设计中落实，不能删除旧任务再冒称恢复成功。

### 功能05 定时、循环、分组与并行调度
总纲对应：功能05。
使用者与前置条件：已授权目标设备和已校验的任务计划。
输入与主流程：复用 Job（父任务）、DeviceJob（设备任务绑定）及 Task（单次执行记录）；每台手机每一轮运行关联独立手机收据，不用一条设备绑定覆盖全部历史轮次；立即执行或按明确时区持久化调度；每次循环生成可追踪的一次运行，各手机有独立收据；按服务器限额有序派发。本轮先实现单机一次立即执行，分组、定时和循环作为正常闭环之后的阶段，不要求先完成所有调度细节才开始单机工作。不同手机可并行，同一屏幕上的脚本、原生 AI、BK 和人工操作必须互斥，包括用户直接在手机上启动的独立 BK 任务。服务器失联、进程重启、锁超时或桥接重建不能单独作为手机空闲证据；恢复派发前必须核对手机实际占用和旧执行者。占用不明时不得授予新屏幕执行权。人工接管须记录原自动任务已暂停还是已停止，只有明确结束接管且原任务恢复条件满足后，才可恢复自动执行。网页接管、手机端暂停／停止和直接触屏分别记录实际覆盖；不能用服务器锁推定所有直接触屏均已受控。首轮正常运行期间无人同时操作手机，并验证已有暂停／停止／接管入口；未接入的直接触屏不列为已覆盖，后续仍须完成总纲要求的人工接管优先。
输出和可观察行为：父任务显示总数及分项状态；手机忙碌显示等待／冲突原因，不全局把所有手机串起来；关闭网页仍可到点启动。
边界、失败与恢复：定时错过、离线、上次循环未完成、组成员变化及夏令时影响均不得无记录补发。错过执行的补跑规则、循环次数缺省与组成员策略待确认；在未决条件影响真实执行时要求用户明确，而不是猜测。取消父计划要区分“停止后续轮次”和“同时停止当前运行”。取消意愿须持久保存为派发屏障：取消生效后，不得再派发该次取消范围内尚未开始的目标或后续轮次；并发派发、服务器重启和自动重试都必须重新检查屏障，不能复活已取消计划。仅对本次取消范围内、已经在手机执行的任务显示停止待确认，直至收到实际结果；仅停止后续轮次时，不向当前轮发送停止请求，当前轮已运行及尚待派发的设备保持原执行计划和状态。
权限、保真或兼容限制：调度与实际执行前均检查设备权限；分发对象不能越过确认的范围。业务发布或消息操作不得凭模糊群体描述无限扩展。
实现说明：把现有单机 BK 任务与原 Job/DeviceJob 关联，保留原 request_id 和远端 task_id。每次逐机运行的稳定关联与 request_id 必须在首次发送前持久化；BK 受理后而服务器尚未收到或保存 task_id 时，仍须按该稳定身份查回原执行或安全证明未受理。无法确定则进入状态待核对，不换 request_id、不创建替代任务、不更换接口盲重发；相同身份重复投递不得创建第二次业务执行。手机已有稳定请求标识及持久收据，服务器也已先保存收据再派发；复用这些基础核验跨端查回契约，不再造另一套任务编号。同一请求重复提交及首派响应丢失的短验证应在首轮真实长任务前完成。纠正 count（计数／时长字段）与时间戳混用及截止比较方向问题；分开保存调度时刻、目标时长与通信超时，禁止用单一 timeout 代表全部概念。现有互斥代码先复用并核实恢复行为，不无依据添加重复锁体系。

输出和可观察行为：同一任务可看到服务器计划与 BK 执行结果的关联；两端 Key 不同仍可工作；无需把手机素材大文件交给服务器模型来完成任务理解。
边界、失败与恢复：BK 模型额度不足、权限缺失或目标无法执行时返回明确失败／待处理；不伪装为服务器调度成功。PIGEON 脚本不是天然能直接放到 BK 运行的同一格式，未提供格式适配前不得宣称全部脚本可跨端无损执行。

实现说明：复用 `mika_run_task`、`mika_task_status`、`mika_list_tasks`、`mika_cancel_task`、`mika_answer`；`mika_wait_task` 与 `mika_steer_task` 虽在 BK 存在，当前桥接未全部映射，只有服务于已确认需求时再补。禁止提交响应不明时改走另一路接口重复发送。

### 功能07 状态、交互、停止和结果
总纲对应：功能07。
使用者与前置条件：用户具有该任务查看或操作权限。
输入与主流程：网页通过父任务查逐机进度，服务器保存 BK 收据和进度。正常执行由手机自主持续运行，服务器按可配置的低频节奏同步进度，不持续获取手机屏幕、不逐步向手机发动作指令，也不持续调用服务器模型判断手机画面。每10分钟一次仅是首轮建议配置，未作为已确认数值。普通进度可复用已有任务接口低频查询；异常和终态另有独立获知路径。实施时核实既有认证通道的事件通知、可取消等待调用或等效能力，采用满足本轮时延的简单实现，不新建手机公网入口或通用推送平台。纯低频查询只能按其查询周期获知结果，不能承诺在下一周期前获知；不满足本轮时延时须补齐通知或等待能力。连接正常时异常和完成不故意等待下次普通进度周期；无法上报时本地保存，重连后补齐，不能冒称实时到达。定期状态仅代表该时点与已记录进度，不作为持续观察全程的证明。用户主动查看或停止仍按权限触发必要查询／控制，不受普通进度周期强制等待。任务等待普通信息时显示问题并传回答复；遇到人工批准、支付或系统权限操作时，网页显示等待原因、所需处理人及真实处理入口。若现有能力仅能在手机处理，应明确提示用户到对应手机的 BK／系统界面操作，而非提供虚假的网页批准按钮；普通追问回答不能代批。批准、拒绝、取消或问题过期后都应反馈到原任务，入口不可达时显示受阻原因；用户停止后立即显示停止中／停止待确认，发送取消并持续核对手机实际终态；不能只保持“运行中”而不展示停止请求，也不能仅按接口接受状态释放设备占用。完成后立即按实际结果归档文本、日志和可用截图，不增加固定五分钟等待。

边界、失败与恢复：取消请求发出不等于已停止；断网时显示停止待确认；过期或乱序结果不能把已终止任务改回运行中。进度未知时显示未知，不虚构百分比。截图不可用时明确缺证据，不伪造截图。首轮需要与原任务关联的真实结束截图，可复用兼容手机或桥接的截图能力，在结束时采集一次；不要求先恢复旧安装包的专有自动归档。至少保留设备、任务、实际执行显示、采集时间和证据来源；截图须对应该任务的执行画面，不能把其他显示或后续任务画面当作结束证据。结束后补采必须标为补采，不能冒充结束瞬间截图。缺少旧归档方式不阻断开发和局部验证；缺少实际截图时只能报告已通过的运行部分，验收08的完整首轮不得判通过。
权限、保真或兼容限制：只展示用户有权访问的任务、截图和必要日志；敏感截图的存储期限和下载权限待确认。只有相应权限的人可回答问题或停止任务。每个答复必须绑定 task_id（任务编号）和 question_id（问题编号）或等效问题版本，仅当前未解决问题可以接受；延迟、重复或旧问题答复不得落到新问题上。
实现说明：映射 BK 业务状态和服务器状态，保留源时间、接收时间和最后成功查询时间。目标进度刷新时延、终态最大展示延迟需要在后续验收参数表中明确，当前不编造秒级承诺。

### 功能08 长任务与安全恢复
总纲对应：功能08。
使用者与前置条件：已安排的长任务及可持久化任务收据。
输入与主流程：首轮由 BK 在单台手机本地自主持续浏览，服务器只登记一次任务并低频同步状态。BK 按计划时长执行，运行中保存必要进度，到期自行结束并返回结果，不依赖服务器每一步确认。首轮先跑正常两小时闭环，遇到实际阻碍再按真实日志处理；复杂手机重启、服务器故障和副作用恢复专项后续开展，不把全部异常矩阵完成作为开始正常闭环的前提，但提交去重、同屏互斥和真实停止状态不能省略。真实长任务之前先用合成／脱敏短任务验证同身份重复或并发提交、首派响应丢失后查回，以及停止接受与实际停止的区别；这些最低契约通过后再进入真实两小时运行，完整重启和副作用恢复矩阵继续后置。通信中断先标记连接异常，重连先按原任务标识查询；手机或服务重启后对照持久收据，区分完成、可恢复、需重新评估及结果不明。原任务目标和已经完成部分保留。
输出和可观察行为：两小时任务不会因统一十五分钟限制被截断；完成后可看到结果；断线恢复不重建一份相同任务。对于八小时等更长目标，时长参数不人为固定成两小时，但真实支持上限须通过后续验证公布。“两小时”究竟指累计实际执行时间，还是包含离线／等待的自然经过时间，需在任务计划中明确；该语义待确认，未明确不得以恢复为由无限延长任务。业务停止期限与完成当前安全收尾分开记录，超期收尾要可见，不能静默计为准时完成。记录自然经过、有效执行及暂停／等待时长；未确定计时语义前不把等待时长冒充有效浏览。计时到期但进展不足时如实报告未完成部分，不因为计时结束直接报成功。
边界、失败与恢复：通信超时不等于业务失败；无法确认已发布、评论或发送时，先查询应用结果或等待处理，不能盲重试。浏览等可重复行为与发送等有外部影响行为采用不同恢复策略；恢复不承诺从任意内存步骤无缝续跑。
权限、保真或兼容限制：按原授权任务范围恢复，不将失败目标扩展为新目标；人工接管优先，自动任务在接管期间不得争抢屏幕。
实现说明：服务器和手机共同保存任务标识、阶段、最后结果、请求幂等键和恢复原因。桥接保留 request_id；BK 重启后访问令牌轮换不改变业务任务身份。执行超时、等待用户、离线等待和计划时长分别处理。已核实本机监督上限候选为3小时，默认仍为15分钟；历史阶段记录称该服务器与网页修改当时未部署，本轮未复核当前部署。复用候选修改并核对实际发布版本，不把放宽监督时限当作手机业务计时已经实现。

### 功能09 分阶段容量交付
总纲对应：功能09。
使用者与前置条件：项目管理员，已具备相应数量受管手机和可观察的服务器资源。
输入与主流程：先完成一台手机、立即开始、只浏览不点赞／评论／关注／发消息的约两小时正常闭环；随后接入分组、定时和循环，再进行16台阶段；按实际瓶颈调整分发和查询，之后设计300／3000台的部署和并发验证。16台是设备规模，不默认代表16路同时执行，也不能仅凭16台分批短任务就宣告并发或长任务验收通过；每阶段先锁定下方参数表再执行。进入后续阶段前解决影响前一阶段目标的实际失败问题；与首轮无关的待决规模、复杂恢复和跨版本事项不阻塞正常闭环的计划与实现，但在进入其对应验收前仍须满足门闸。
输出和可观察行为：每阶段有设备数、并发数、任务类型、服务资源、结果统计和异常记录；对外只标注已经验证的规模。
边界、失败与恢复：注册设备数不等于同时执行数；队列可接受不等于手机任务成功。大规模必须包含离线、忙碌、慢机和部分失败，不用纯空任务代替实际业务容量结论。
权限、保真或兼容限制：测试范围和外部影响另行授权；模型预算、费用上限和并发上限待确认，未确认不启动大量收费调用或外部发送。
实现说明：优先复用现有任务体系进行限并发、分批派发和状态采集；是否需多进程或多节点以实际测量决定，本文件不预先承诺某一种基础设施或一台服务器承载3000台。
