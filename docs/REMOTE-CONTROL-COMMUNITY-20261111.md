# 开源传屏方案核查与下一步（2026-11-11）

本文件在本轮修复、部署和实机记录完成后整理。结论是保留 PIGEON 管理和现有 WebRTC/P2P，优先改进编码器兼容与媒体队列控制；没有证据证明整体换成另一个后台就能解决这台手机的长尾。主界面、main、Root 状态均不变。

| 项目 / 官方资料 | 可核实的处理方法 | 对本项目的适用边界 |
| --- | --- | --- |
| [scrcpy 视频文档](https://github.com/Genymobile/scrcpy/blob/master/doc/video.md) | 调低尺寸和码率；按编码器要求对齐尺寸；编码失败降尺寸；默认不额外缓存视频 | 正好对应本轮 480 档配置失败。尺寸不能仅按比例猜测，需核对真实编码器能力。额外 50 ms 缓冲可减轻抖动，但同时增加延迟 |
| [scrcpy SurfaceEncoder](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/video/SurfaceEncoder.java) | 使用实时优先级、低延迟编码提示、静止画面重复帧；初始化失败时有能力约束及有限次数回退 | 可参考参数和生命周期，不应把 scrcpy 宣称的本地链路延迟当作本项目 5G 保证；FIRERPA 原生模块的可配置能力还需核对 |
| [RustDesk VideoQoS](https://github.com/rustdesk/rustdesk/blob/master/src/server/video_qos.rs) | 区分路径基线与视频队列额外延迟；确认拥塞后降码率/帧率，良好样本后恢复，避免一次抖动就剧烈变档 | 当前控制 RTT 快而视频慢，不能仅用 ping 判定网络良好。下一步重点应是逐段媒体耗时和码率，而不只是继续压低 FPS |

同类问题证据：[scrcpy #7098](https://github.com/Genymobile/scrcpy/issues/7098) 报告另一款芯片/固件在 MediaCodec 配置阶段失败，讨论编码器回退。它仍是开放的提议，不能说官方已实现，也不能把其中固件根因套到我们的 vivo 上；但说明仅更换公网线路不能修复编码器初始化失败。

## 缓冲的选择

采用低延迟、容量受限的缓冲；解码后的待显示帧可以被更新帧覆盖（可参考 [scrcpy frame_buffer.c](https://github.com/Genymobile/scrcpy/blob/master/app/src/frame_buffer.c)）。编码的 H.264 帧存在参考关系，不能把任意 P 帧当独立图片随意丢弃；过期后需等可解码的关键帧。本轮已保留这个约束，浏览器抖动缓冲设置仅为提示，不是强制保证。

不采用几秒的视频积压来“看起来流畅”。私信和发布任务更需要当前画面与点击一致；静止清晰补图必须能在输入/新变化时撤销，不能把缓存截图当成实时画面。

## 下一轮顺序与验收

1. 把手机编码出帧、发送、接收丢包/重传、抖动缓冲、解码的时间增量放到同一次动作记录中。先定位 1.8–2.7 秒尾延迟；不拿控制 RTT 替代画面延迟。
2. 查询这台手机的编码器尺寸、对齐、码率能力。为不兼容配置选择有效尺寸/编码器；目前会话级降档已部署，能力预检尚未完成，不能声称 480 原生编码已修好。
3. 参考 RustDesk，优先调码率并控制排队，再决定是否改 FPS/尺寸。现有 API 若不能可靠调节这些参数，单独评估替换采集编码组件，保留管理后台与鉴权。
4. 同一台纯 5G 手机、同一浏览器前台，至少 30 次点击/滑动，分别报告 P50/P95、首帧时间、失败次数和断网恢复时间。测试浏览器受限到 1 Hz 时，只报告解码帧观测并标明限制，不据此宣称显示性能通过。

国内服务器只作为中继/管理链路的对照方案：本轮媒体已观察到 direct UDP，当前端到端尾延迟不能直接归因于香港服务器，也不能承诺迁移即可解决。
