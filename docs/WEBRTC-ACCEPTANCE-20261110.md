## 已核实

- 本机 SpeedCat 持久名单与 Windows WinINET 均包含业务域名直连规则。浏览器新 API 请求实际连接服务器公网 IP 的 443 端口，没有经过本机 7890 代理。其他电脑需分别设置自己的代理。
- 无 Root 的当前 vivo 手机恢复接入。手机 FIRERPA 重载后有残留进程，启动日志报 `already running`；通过原有 Termux / SSH 无线 ADB 隧道，仅处理 UID 2000、可执行文件属于已知 FIRERPA 目录的残留进程，从子进程调用原版启动器恢复。未启动 STF 应用，未修改证书、设备配置或手机数据。
- 单独 STUN 协商获得候选，但当前两端 ICE 探测无响应。部署鉴权 coturn 后，实际选中 WebRTC H.264、UDP relay 路径，媒体 RTT 常见约 158–190 ms。**RTT 不是点击端到端延迟。**
- TURN 约占 5.4 MiB 内存；当次 PIGEON 容器约 529 MiB，CPU 约 4.3%，仅为该时点读数。
- ICE API 经设备权限校验后返回短期凭据，响应 `Cache-Control: no-store`；无登录请求返回 401。共享密钥不进入前端、日志证据或 Git。
- 测试页主动注入 RTC 断连：备用 H.264 首帧约 1537 ms，重新切换 WebRTC 约 5124 ms；原触控 socket 保持在线。单独断开触控也自动恢复，视频保持 WebRTC。暂停后媒体 / 触控连接释放，状态通道保留，恢复后重新出 WebRTC 画面。
- 10 项连接 / 生命周期自动检查、TypeScript 类型检查、生产构建通过；后端签名 / 权限检查与原 telemetry 检查通过。生产构建仍有项目原有大 chunk 提示。

## 性能验收结果

在设置列表连续滚动时，一个 10 秒窗口解码 151 帧（约 15.1 fps），没有新增丢帧；但 Canvas 只绘制 23 帧。进一步用独立 requestAnimationFrame 计数发现测试浏览器 3 秒仅执行 5 次，即浏览器自身约 1.7 fps。页面报告 visible / focus，窗口工具却连续两次 `window capture timed out`；自动激活窗口和 bringToFront 没能解除限速。不能据此断言手机端编码能力不足。

在同一受限环境，30 次黑白目标点击得到中位 1020 ms、P95 1069 ms、最大 1101 ms。计时是网页触控 up 发送到 Canvas 出现目标颜色，使用同一 performance 时钟。**这些数值受验收浏览器绘制限速污染，只作为诊断证据，不作为优化后的体验承诺或与旧方案的有效对比。** 临时将视频挂载到可见区域未消除浏览器动画帧限速，没有将这个实验改入产品代码。

用户恢复窗口后仍出现浏览器绘制限速。最终对两组均启用临时 CDP 16×16、低质量画面采集，让测试浏览器持续绘制；独立 requestAnimationFrame 计数恢复约 60 fps，采样结束立即关闭，不改变产品代码。以下测量因此是浏览器回传画面的延迟与到帧数据，不是外部高速相机测得的物理屏幕发光延迟。

手机在验收期间从 Wi-Fi 切换到移动网络（`rmnet_data3`，未由本任务修改网络设置）。**以下有效对照均在该移动网络上完成，WebRTC 实际选中 srflx / srflx UDP 直连；不能把这些延迟当成之前 Wi-Fi 经 TURN 中转的成绩。** 同一手机、同一浏览器、540×1194、15 fps 请求、质量 25，均绕过电脑代理。两组按顺序取样，网络仍可能波动，不是长期容量测试。

| 项目 | 原 H.264 / WebSocket | 新 WebRTC |
| --- | ---: | ---: |
| 黑白目标点击有效样本 | 30 / 30 | 30 / 30 |
| 点击到回传画面中位数（两个中间值平均） | 1151 ms | 619 ms |
| 点击 P95（nearest rank） | 1962 ms | 873 ms |
| 最大点击回显 | 2066 ms | 1132 ms |
| 连续动画实际绘制，20 秒 | 301 帧，15.05 fps | 295 帧，14.75 fps |
| 两个 10 秒窗口到帧间隔 P95 | 148 / 150 ms | 100 / 100 ms |
| 窗口内最长到帧间隔 | 1245 ms | 118 ms |

WebRTC 点击中位数降低约 46%，P95 降低约 56%。连续动画窗口 WebRTC 解码 300 帧、无新增丢帧或丢包，媒体 RTT 48–55 ms。动画为测试网页上持续左右移动的色块，说明这个负载下的稳定性，不代表复杂视频或所有 App 都有同样帧率。设置列表滚动的第二轮控制任务未完整结束，未计入有效对照；正式动画目标由截图确认后采样。点击预热曾出现一次等待超时（当时尚未稳定切入 WebRTC），没有并入正式 30 次样本。

结论：本轮主要改善回传延迟和到帧均匀性，未提高原本请求的 15 fps 上限。触控 / 导航仍通过 WSS 与香港网关，直连视频不能消除这一段耗时；约 0.62 秒的中位点击回显仍有优化空间。下一步应优先比较国内就近控制网关 / TURN 与现有节点的同条件数据，再决定迁移，不将“换服务器”当作已经验证的万能解决办法。

机器可读结果见 `docs/benchmarks/webrtc-20261110.json`；原始小型诊断证据仍保留在本机任务目录。

按用户随后明确的日常页面操作、发布与私信用途，本版作为小批量人工真机试用里程碑；适用性、尚未测清的分段延迟和后续优化顺序见 [试用计划](PILOT-PLAN-20261110.md)。这不代表 AI 业务流程或十台并发已经验收。

## 恢复与运行边界

- 前端可用已有发布脚本切回界面里程碑；地址加 `?transport=ws` 只在当前页面关闭 WebRTC。
- 当前 TURN 支持 UDP / TCP 3478，媒体中转端口 UDP 49160–49200，已在主机和阿里云防火墙精确放行；不宣称支持只允许 TLS 443 的网络。
- 停用 TURN 可以 `systemctl stop bk-turn`，前端仍有 WSS 回退。只恢复前端无需重启手机。API 的旧路由文件小型备份在服务器 `bk-server/bk_telemetry.before-ice-20261110.py`；负责人为本任务用户，复查日 2026-11-17。
- 本轮复用原工作区、依赖与运行环境，无新工作树。详细小型统计和恢复证据位于本机 `phone-pilot-20261108/browser/bk-webrtc-20261110/`；不包含 TURN 密钥或可用凭据。
- 本机和服务器各清理 3 个已传完的临时构建包，分别约 13.39 MiB；保留已解压发布、回滚信息和小型证据。临时验收网页测试后删除，手机回到桌面，临时 ADB 工具容器恢复停止状态；未启动 STF 栈。
