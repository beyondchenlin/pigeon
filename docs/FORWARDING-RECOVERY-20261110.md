# 云端转发断线：修复与验证（2026-11-10）

> 本文保留较早阶段的诊断结果。后续已定位 20 秒重连退避，并切换到 `0.72.0-bk.1`；当前安装包、实测速度和键盘操作见 [快速重连与键盘验收](RECONNECT-AND-KEYBOARD-20261110.md)。以下旧版安装包不可直接搭配最新安装器。

## 确认的事实

- 手机为 vivo V2220A，Android shell UID 2000，未 Root。排查中手机本地 RPC 多次为 28–155 ms，但云端请求曾超过 4–8 秒。心跳和远控是不同通道，不能用设备“在线”代替可控验证。
- 原手机客户端实际上是 C 实现 `xfrpc 5.09.976`，服务器是官方 `frps 0.71.0`，不是同一版本的官方客户端/服务端组合。日志出现控制连接关闭、申请工作连接超时及重新分配端口。
- 异常时观测到 FRP TCP 重传、专用 SSH RTT 一度约 2.27 秒及心跳延迟。用户确认亮屏解锁、Wi-Fi 未变；后续 DeviceIdle 为 ACTIVE，Termux 持有唤醒锁，Wi-Fi RSSI 约 -55 dBm。**这不等于已经证明运营商线路是唯一原因**。
- 后续发现服务器实际内存约 1.64 GiB，诊断时可用内存一度约 145 MiB，memory PSI 的 full avg60 约 17%。本次两个并行的 SDK/数据库诊断程序各额外占用约 70 MiB，增加了压力。已停止这些重复采样程序；可用内存回到约 208 MiB、full avg10 低于 1%。后续只运行一个有界采样器，不把诊断负载造成的停顿归因于地域。
- 旧实现存在协议/恢复兼容性疑点，但没有取得可证明具体 C 源码缺陷的堆栈；不能把某条上游修复说明当成这台手机的唯一根因。仅更换客户端后仍观测到网络波动，所以也不能宣称单换客户端即可消除所有断线。

## 实际修改

1. 手机改用官方 Android ARM64 `frpc 0.72.0`，由原 FIRERPA 服务管理。`bk_frpc_adapter.py` 只适配原 `xfrpc -f -c ...` 的启动参数，然后 `exec` 官方程序；不另开第二个守护进程。仍读取本机生成的 `fwd.toml`，保留设备身份、TLS、加密、认证和目标端口。
2. 云端转发服务升级为官方 `frps 0.72.0`。该版本明确修复失效/替换控制连接的复用会话释放，以及 yamux 关闭阻塞拖延重连的问题。没有取消认证插件、关闭心跳、放宽 TLS，或单纯延长超时掩盖断线。
3. 既有等待本机认证服务就绪的启动顺序保留；热部署仅替换/重启 `service:frps`。持久化启动器和程序位于 `/user/phone-pilot`，容器重建后仍使用；源码镜像构建也固定为 0.72.0。
4. 手机安装器检查 UID、架构、目录、程序 SHA-256、原生配置兼容性，并保存原程序和安装清单。重复安装不会重启已经运行的官方客户端；发现 App 更新改变入口时拒绝直接覆盖。提供单独回退操作。
5. 加入 `ops/check_bk_forwarding.py`，分别记录心跳新鲜度及真实认证 RPC 结果。它只读，不自动重启服务，不输出证书、密钥或屏幕内容。

手机主服务在以上切换及故障注入中保持原 PID 18561，官方转发进程 PID 31643 自行处理重连。前端、main、手机 Root 状态均不改动。

## 验收口径

在服务器容器网络命名空间内，仅对这台手机的 FRP TCP 17000 连接双向丢包。分别测试 20 秒、105 秒；有独立超时撤销及 finally 清理，记录实际 DROP 包数和规则删除结果。SSH、MQTT、其他服务不在故障注入范围内，因此这是**手机到云端转发链路断网**，不是手机整机飞行模式/重启测试。

每 5 秒通过云端网关创建认证连接、请求真实设备信息，每分钟请求一次截图但不保存图片。请求恢复时间包含新建 TLS 连接和最多 5 秒采样误差，不等于用户点击延迟。双端 0.72.0 下，20 秒丢包后的首次成功 RPC 约在恢复后 14.96 秒，105 秒丢包后约 3.71 秒。两次测试均撤销了精确的故障规则，主服务和客户端 PID 未变。

最终阶段 177 次采样中 105 次成功、72 次失败，包含人工故障、自然异常及诊断内存压力；**持续在线验收未通过，不能把升级标记为断线问题完全解决**。还测试了 Wi-Fi 关闭 60 秒后恢复：手机切到移动数据并重新接入，随后 Wi-Fi 恢复；这不是飞行模式断网，不能冒充完全断网验收。

测试期间也发生了非注入的网络波动，这部分失败保留在原始记录中；不能从成功率里悄悄删除后宣称全程零故障。持续在线只能按实际观测时间报告，不能写成 24 小时或 10 台设备已通过。

## 画面通道的独立故障

后续复现控制 RPC 正常、网页 WebSocket TLS 握手超时；手机本地 TLS 同样超时，排除了仅靠云端地域解释该次故障。发现当前主服务下一个 Python 子进程长时间等待 futex，SIGTERM 无法退出。核对 UID 2000、可执行文件、父 PID 和启动时间后，仅结束该子进程，手机本地 TLS 立即恢复，浏览器 WebRTC 随后直连。手机主服务 18561 和 frpc 31643 未重启。

这证明该子进程阻塞与网页通道不可用直接相关，但尚未取得原生模块的 Python/C 堆栈，不能宣布已修复其内部锁缺陷。旧 H.264 回退采屏、WebRTC 并行启动和重连是触发条件的排查方向；网页侧改进及后续实测另见 `VIDEO-RETURN-20261110.md`。另清理了已确认属于旧平铺运行目录、PPID=1 的遗留采屏/配置进程；该清理本身没有恢复 TLS，不将它写成此次唯一根因。

新手机需先完成自己的 FIRERPA 配置和授权；不要复制第一台手机的配置、证书或身份。当前安装器仅支持 ARM64 + shell 模式。把验证过的官方 `frpc` 命名为 `frpc-0.72.0-android-arm64`，与适配脚本放入该手机自己的 `$USRDIR/phone-pilot`。用该手机原生 Python 执行：

```sh
"$ROOTDIR/bin/python3" "$USRDIR/phone-pilot/install_bk_frpc.py" \
  --runtime-root "$ROOTDIR" --user-root "$USRDIR" --activate
```

`ROOTDIR` 必须是 App 实际使用的运行目录；当前手机为 `/data/local/tmp/CnyL76/server`。`USRDIR` 当前为 `/data/local/tmp/CnyL76/usr`，解析到 `/data/local/tmp/usr`。安装器不会猜测目录，不负责授予 Shizuku 权限。

手机回退：同一命令增加 `--rollback`。这会恢复原客户端，并仅切换转发子进程；原配置和数据不变。整机重启后仍需按 Android/Shizuku 的原有授权机制启动，不宣称免授权永久驻留。

服务端回退：核对恢复文件 `ops/frp-stability-20261110/wait_auth_then_frps.before.py` 后，恢复持久化 `data/user/phone-pilot/wait_auth_then_frps.py`，再仅重启 `service:frps`。原镜像 `/usr/sbin/frps` 没有被覆盖。
