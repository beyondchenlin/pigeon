# BK 群控：WebRTC 试用里程碑与下一步计划

日期：2026-11-10（北京时间）。用户本轮明确用途为账号日常页面操作、视频发布、私信查看与回复，以及后续 AI 执行这些任务；无需以连续观看高帧率视频作为主要目标。继续在 `dev` 开发，保持界面与 `main` 不变。

## 决定

当前版本适合进入小批量真机人工试用，保存为 `bk-v0.3.0-webrtc-pilot` 预发布里程碑。现有传输代码、生命周期测试和测量数据已在 `dev`，不制造重复合并。当前网页点击回显的中位数约 0.62 秒、P95 约 0.87 秒、动态画面约 15 fps，可以作为这些业务的人工操作基线。

这是远控基础能力的试用版，不代表 AI 自动发布 / 私信工作流已经开发或验收，也不是十台并发、长时间稳定性的结论。0.62 秒是浏览器发送触控 up 到回传 Canvas 像素变化的实测值，不是手机接到指令的时间，也不包含 AI 推理、素材上传或平台处理耗时。

历史调查曾提出 P95 不超过 350 ms 的低延迟目标，本版没有达到；根据本次用途调整，先验证任务可靠性。旧目标、原始结果与未完成的多机 / 长时验收保留，不改写为已通过。

## 0.62 秒目前能定位到哪里

| 环节 | 现有证据 | 判断 / 尚缺信息 |
| --- | --- | --- |
| 浏览器发送触控 → 云端 → 手机 | 代码仍走 `/ws/screen/touch`，经香港鉴权网关和手机反向隧道；down / up 直接发送，没有人为固定 600 ms 等待 | 首要排查对象之一；暂无每条触控的手机接收 / 执行确认，不能量化占比 |
| 手机输入处理、App 响应、采集与编码 | 未取得同一次点击的逐段时间戳 | 与控制网络一起排查，不能把这段统称为网络延迟 |
| 视频网络 | 有效对照在移动网络，WebRTC 选中 srflx / srflx UDP 直连，媒体 RTT 48–55 ms | 这一组媒体没有绕香港；RTT 不是单向传屏或点击耗时 |
| 浏览器媒体缓冲 | 20 秒动态样本的累计 jitterBufferDelay 增量 / emitted 增量约 44 ms | 有开销，但不能单独解释 0.62 秒 |
| 浏览器解码 | 同窗口 totalDecodeTime 增量 / framesDecoded 增量约 0.53 ms / 帧 | 本次样本没有显示解码是主要瓶颈 |
| 采集 / 绘制节奏 | 请求 15 fps，帧周期约 67 ms，实际绘制约 14.75 fps | 提高帧率有带宽成本，本用途不优先提高 |

上述指标来自不同统计口径；不把 RTT 除二当成可靠单向测量，也不相加 / 相减制造完整的 619 ms 分段预算。数据和浏览器受限样本的排除理由见 [验收记录](WEBRTC-ACCEPTANCE-20261110.md) 与 [机器可读结果](benchmarks/webrtc-20261110.json)。

## 国内服务器是否更好

对于在国内的手机和操作者，国内就近节点是合理候选，可能缩短控制、API、TURN 中转及 WSS 回退的路径。阿里云官方也将距离和网络质量列为地域选择因素。但当前有效样本的视频已直连，单纯搬网页静态文件、信令服务或只换 TURN，不能保证触控随之变快。

如果做地域对照，需要让被测手机实际接入候选节点的控制网关 / 反向隧道，保持同一代码、手机、运营商、代理策略及画面参数。香港与候选国内节点交替测试，分别记录直连与中转，不混合不同网络的结果。节点应同时靠近实际手机与操作端；现在不凭空指定某个城市，也不购买或迁移现有服务。

建议决策条件：候选节点在至少两个实际网络、每组至少 30 次点击中，点击 P95 稳定改善约 25% 或以上，且任务成功率与重连表现不退步，再考虑迁移。25% 是本项目的取舍门槛，不是厂商承诺。

## 接下来按这个顺序做

### 1. 固定当前版本，先收集真实使用反馈

- 先 2–3 台不同型号 / Android 版本，再逐步扩到目标 10 台。先验证多台接入与日常操作，不一次打开十路详情视频；卡片预览也计入带宽和负载。
- 每台至少一次 30 分钟人工操作和一次 2 小时在线观察。用同一网络记录点击、文本输入、滑动、返回、断线恢复。重复出现的问题记录时间点，便于对照服务端日志。
- 小批量检查 CPU、可用内存、OOM、流量和连接数；当前小内存服务器只验证过单机，不把“已接入十台”等同于“十台并发任务已通过”。

### 2. 后续二开优先做任务执行可靠性，界面保持不变

- AI 任务走后端设备接口，人工远控页用于观察与接管；先核实并复用已有作业 / 设备能力，不让自动任务依赖某个浏览器标签页一直在前台。
- 每台手机串行执行动作，完成后读取最新页面状态再继续；优先可用的控件 / 文本信息，必要时取清晰截图交给视觉模型。读取小字与私信时，不仅依赖半分辨率预览。
- 等待条件使用页面变化 / 控件出现 / 操作结果，不用一串固定延时猜测执行成功。记录任务 ID、步骤 ID、耗时、失败原因，避免旧截图驱动下一步。
- 发布、发私信等操作必须核对目标账号 / 会话与结果；断线后先检查是否已成功，结果不确定则标记待确认，不能盲目重发。任务级去重不能被描述为第三方 App 已提供严格的 exactly-once 保证。
- 视频素材传输、上传进度和平台处理单独统计；发布耗时不以传屏 fps 评判。私信先验证收件人、文字识别与发送状态；本轮未向任何真实用户发消息，也未发布内容。

### 3. 对确实影响任务的延迟，再分段优化 / 对照国内节点

- 加入可开关的诊断记录，不增加页面控件：动作 ID、浏览器发送与绘制、服务端转发时长，以及设备端可取得的接收 / 完成信息。日志不记录消息正文、截图、令牌，按现有轮转规则限制容量。
- 原生触控通道没有现成逐动作 ACK；先验证上游能力或用独立诊断接口。不能把“socket 已发送”视为“手机已执行”，也不承诺纯前端就能获得手机内部时间戳。
- 各端使用本地单调时钟计算本端区间，以往返测量和动作 ID 关联结果；没有时钟校准时，不直接相减跨机器时间戳。低开销 status 往返只用于定位网络趋势，不冒充触控执行时间。
- 如果主要时间落在跨地域控制链路，再按上节做国内节点 A/B；如果主要落在设备输入、App 等待或采集编码，先处理对应环节。没有确认手机端支持前，不规划“只加前端 DataChannel 就实现 P2P 触控”。

以上是后续实施顺序，本次只固定已验证的传输版本与计划，不夹带新任务引擎、未验证协议或服务器迁移。

| --- | --- | --- | --- | --- | --- | --- |
| 待填写 | 待填写 | 待填写 | WebRTC / H.264 / 兼容模式 | 点击 / 输入 / 发布草稿或视频 / 私信 | 待填写 | 待填写 |

先采用以下试用门槛（目标，不是已达成的多机结果）：

- 每台 30 次可确认结果的基本操作，至少 29 次一次完成；点击回显 P95 尽量在 1.5 秒内，超过则保留时间点和网络信息。
- 当前截图可辨认文字、手机状态准确；发现旧画面继续执行、错设备 / 错会话、重复发布 / 发送，立即停止对应任务并保留最小证据。
- 发布和私信以结果正确、无重复为验收重点；网络可用后通常 10 秒内恢复可用，超时、需要手动重启和丢失进度分别记录。
- 零错对象、零重复执行是正确性门槛；有限样本为零并不证明以后绝无错误。
